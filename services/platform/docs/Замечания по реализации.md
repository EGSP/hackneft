# Замечания по реализации платформы

Разбор ветки `feat/platform/sqlite-integration` (коммиты `ad02510`, `a0cdff2`, `f69f1e8`) после слияния в `feat/ai-service`. Замечания сгруппированы по степени важности: первый раздел — расхождения с оговорённой архитектурой, остальные — дефекты и качество кода.

## 1. Расхождения с оговорённой архитектурой

### 1.1. Нет механизма подписки на события

Оговаривалось: платформа публикует событие «поступили новые данные», а обработчики подписываются на него, не изменяя код приёма данных.

Сейчас эндпоинт `POST /api/sensor-data` (`api.py`) сам вызывает двух конкретных получателей:

```python
sensor_tag_observer.notify(sensor_data.sensor_tag)
background_tasks.add_task(ai_agent_event_handler.handle_sensor_data_created, ...)
```

- `SensorTagObserver` не реализует паттерн Observer: у него нет списка подписчиков и метода подписки, это объект с одним методом, который вызывается явно. Метод только печатает тег.
- Добавление любого нового обработчика требует правки эндпоинта.
- Обработка одного события разделена на два механизма (синхронный вызов и `BackgroundTasks`) без общей точки расширения.

Требуется: диспетчер событий с регистрацией обработчиков по типу события и, при необходимости, по коду датчика. Эндпоинт только публикует событие.

```python
@dataclass(frozen=True)
class SensorDataCreated:
    timestamp: datetime
    sensor_code: str
    value: float

Handler = Callable[[SensorDataCreated], Awaitable[None]]

class EventDispatcher:
    def __init__(self) -> None:
        self._handlers: dict[str | None, list[Handler]] = defaultdict(list)

    def on(self, sensor_code: str | None = None) -> Callable[[Handler], Handler]:
        """None — обработчик получает события всех датчиков."""
        def register(fn: Handler) -> Handler:
            self._handlers[sensor_code].append(fn)
            return fn
        return register

    async def publish(self, event: SensorDataCreated) -> None:
        for fn in self._handlers[None] + self._handlers[event.sensor_code]:
            try:
                await fn(event)
            except Exception:
                logger.exception("Обработчик %s завершился ошибкой", fn.__name__)
```

Обработчики размещаются в отдельных модулях и регистрируются декоратором `@dispatcher.on("F6")`.

### 1.2. Платформа привязана к ИИ-сервису

Оговаривалось: механизм хранения и обработчиков не знает об агентах.

Сейчас в платформе есть `AiAgentEventHandler` (`events.py`), который отправляет каждое событие в ИИ-сервис. Кроме того, обращение не работает:

- эндпоинта `POST /agents/run` в ИИ-сервисе нет, каждая запись завершается ошибкой 404 в журнале платформы;
- адрес по умолчанию `http://localhost:8001`, а ИИ-сервис работает на порту 8100.

Требуется: удалить `AiAgentEventHandler` из платформы. Если реакция агента на данные понадобится, она подключается как обычный подписчик диспетчера, а не как часть ядра платформы.

### 1.3. Нет справочника имён и представления для запросов

Оговаривалась схема из двух таблиц и одного представления:

- `sensor_data` — только измерения: время, код датчика, значение;
- `sensor_names` — справочник имён: код датчика и любое его имя (сам код, «ПАК», «ЛИМС», описательное название), первичный ключ `(sensor_code, name)`; исходный код тоже записывается как имя;
- представление `sensor_query` — соединение `sensor_data` и `sensor_names` по коду датчика.

```sql
CREATE VIEW sensor_query AS
SELECT d.timestamp, d.sensor_code, n.name AS sensor_name, d.value
FROM sensor_data d
JOIN sensor_names n ON n.sensor_code = d.sensor_code;
```

Эндпоинт диапазона выполняет один запрос `WHERE sensor_name = :name AND timestamp BETWEEN :start AND :end` и не различает код и синоним: запросы `?name=F6` и `?name=ПАК` возвращают одни и те же измерения, хранящиеся в одном экземпляре.

Сейчас:

- таблица одна — `sensor_data`, в ней вместе с измерением хранятся `sensor_name` и `source`, то есть терминология записана в каждой строке измерений;
- таблицы `sensor_names` и представления нет;
- `GET /api/sensor-data/range` фильтрует по `sensor_tag`, синонимы не поддерживаются;
- перечень кодов `KNOWN_SENSOR_TAGS` задан множеством в `observers.py` и нигде не используется; его место — таблица `sensor_names`.

Представление создаётся не через `create_all`, а отдельной командой `CREATE VIEW IF NOT EXISTS` при инициализации базы (или миграцией, см. 3.1). В SQLAlchemy представление отображается моделью только для чтения либо запрашивается через `text()`.

## 2. Дефекты

### 2.1. Повторная запись приводит к ошибке 500

На таблице ограничение `UNIQUE (timestamp, sensor_tag)`, но `IntegrityError` при `db.commit()` не обрабатывается. Повторная отправка того же показания возвращает 500 вместо 409 либо идемпотентного ответа. Для потоковых данных повторная доставка — штатная ситуация.
